### Aug 25 — Required email permissions: groups, shared mailboxes, Manager role, and private leadership inboxes
Tyler defined the access model needed before the Email Activity module can move beyond admin-only validation. Admins must be able to assign Hub users to **Groups**; each Group carries one or more **shared mailboxes**, and those mailbox grants can be toggled on/off. The Hub needs a third role, **Manager**, alongside Staff and Admin. Manager/Admin personal inboxes must remain private and inaccessible to other users—critically, being a Hub admin must not automatically grant the ability to read another leader's private correspondence. Mailbox administration and mailbox-content visibility therefore need separate permissions. Current-state assessment: the app uses Replit-managed Clerk and an internal staff allowlist, but only has Staff/Admin roles; admins can add an email to the allowlist and that person later signs up/signs in independently, but the Hub does not send a true invitation or provision a Clerk user. The code does not enforce `@mintprintworks.com`, and the default Clerk sign-in component does not itself prove Google-only Workspace sign-in; those providers/domain rules are managed through Replit Auth settings, with a server-side domain check still advisable as defense in depth. Email Activity is currently all-or-nothing admin-only, and its two tracked mailboxes have no owner/shared/group semantics. Required future build: Staff/Manager/Admin role migration, users/groups/memberships, mailbox ownership/type, group-mailbox grants, a centralized authorization policy applied to every email endpoint, admin invitation/pre-authorization UX, and Google Workspace domain enforcement. Development and production Clerk user stores are separate, so rollout/invites must be handled in the intended environment.

### Aug 25 — Email history horizon and Missive as the missing collaboration layer
Tyler questioned whether the email tracker needs its default one-year Gmail backfill and suggested 30 days, then pointed out that Google Workspace cannot supply the internal comments or show who collaborated on a thread inside Missive. **Conclusion: 30 days is a sensible initial Gmail baseline, and Missive can provide the collaboration context Gmail fundamentally cannot.** The existing Gmail tracker is deliberately metadata-only: it stores message direction, participants, subject, timestamps, labels, and thread identity—not bodies or Missive activity. Its first run currently searches `newer_than:365d`, pages resumably, snapshots Gmail's history watermark before starting, then switches to incremental history; an expired watermark triggers a seven-day catch-up. The horizon already exists as a setting but currently applies only to newly added/not-yet-completed mailbox backfills, and the settings screen displays it without an editable control. Missive's current REST API can list historical conversations and separately retrieve external messages, internal comments with authors, assignees, participating users, team inbox, labels, tasks/drafts, contacts, timestamps, and Missive links; rule-driven webhooks cover future activity but are not enough for historical backfill. Recommended future model: keep a 30-day Gmail baseline plus forward incremental tracking for broad/authoritative mailbox activity, and enrich conversations handled in Missive with comments, collaborators, assignments, and labels. Do not show all internal commentary indiscriminately: the Hub must apply explicit staff visibility rules, and the Missive token's own conversation visibility must be tested. Before merging Gmail and Missive records, verify whether the Missive API exposes a stable email identifier usable for exact deduplication; otherwise use Missive conversations as the rich canonical thread and Gmail as the coverage/statistics fallback. Replit has a secure Missive application connector available; no token should be pasted into chat.

### Aug 7 — Feasibility: "CFO AI assistant" — an analyst agent over Printavo + company financials
Tyler asked whether the Hub could host an AI agent that analyzes order-level data (qty, decoration method, pricing, color counts, stitches), imported company financials (payroll/labor by department), and CSR email effort (thread counts per customer/invoice) to make observations about pricing, profitable vs. loser orders, ideal customers, and niches to target. **Answer: feasible, and the Hub is unusually well positioned — but it's a three-layer build, and the AI is the easy layer.** (1) **Data foundation — largely done.** The full Printavo mirror already holds every order's line items, decoration details, pricing, and complete payment history, and the Ask AI page already proves the "AI safely queries our data" pattern (guarded, read-only). (2) **The real work is the cost side.** Revenue per order is known; *cost* per order is not. Payroll/labor by department has to come in (CSV import or simple entry screens first; QuickBooks/payroll integrations later), and then labor must be *allocated* to orders via an effort model — using stitches, color counts, quantities, and decoration method as effort proxies. That allocation model is where profit-per-order accuracy lives or dies, and it should be visible and tunable by Tyler, not hidden inside the AI. Email-effort-per-order depends on the email correspondence hub idea (also logged today) landing first. (3) **The agent layer.** Once cost-per-order exists, the CFO assistant is an extension of the existing Ask AI machinery: scheduled analysis runs producing a digest of observations (margin trends, underpriced work, customer ROI rankings, niche performance) plus an interactive "ask the CFO" chat — always advisory, always showing the numbers behind each claim so a human can check its reasoning. Tyler's instinct that this generalizes is right: the same pattern (local data + allocation model + scheduled AI analyst) works for production efficiency, sales follow-up, and purchasing. Sequencing reality: financial data intake → effort/cost allocation model → AI analyst on top. Logged to the roadmap.

### Aug 7 — Feasibility: email correspondence hub (map sales/CSR email to customers & invoices, CRM-style)
Tyler asked whether the Hub could monitor the sales/CSR email accounts and map inbound/outbound emails to a customer and/or invoice visible here — plus read-receipt monitoring. Motivation: the team finds Printavo's messaging impersonal and prefers keeping correspondence on the customer's original email thread. **Answer: the core idea is very feasible; read receipts are the weak spot.** (1) **Customer mapping — easy and reliable.** We already sync every Printavo customer and contact email into the local database, so matching a message's from/to addresses against known contacts is straightforward; a timeline of real email correspondence on the customer profile is a natural fit. (2) **Invoice mapping — feasible but heuristic.** Emails don't carry an invoice ID, so linking to a specific order means pattern-matching (order numbers/nicknames in subject or body, Printavo links, date proximity to active orders) — expect "probably invoice #X" suggestions with a manual confirm/reassign, not perfect automation. This mirrors how CRM platforms (HubSpot, Pipedrive) do it. (3) **Access path:** the accounts are Google Workspace, so the Gmail API is the way in — per-mailbox authorization (each salesperson connects once) or admin-level domain delegation; read-only monitoring, no sending needed, so the team keeps working in their own inboxes and threads exactly as they do today. (4) **Read receipts — honest caveat:** email has no reliable built-in read signal. Gmail read receipts mostly work only inside the same organization; the industry workaround is a tracking pixel injected into outbound mail, which only works if messages are *sent through* our system (conflicting with "reply from your own inbox") and is increasingly blocked by mail clients (Apple Mail privacy protection fires pixels for unread mail, so it over-reports). Realistic proxy: track *replies* (customer responded = definitely read) rather than opens. Ties into the roadmap's Sales & front-end support tools (follow-up reminders and activity notifications would get much smarter with real correspondence data) and the outgoing-activity-log idea. Logged to the ideas board; nothing built.

### Jul 25 — Decoration methods on the customer profile, and what the Chipply nickname tokens actually are
The customer profile now shows a per-method breakdown ("Embroidery — 40 pcs — 1 order") for both sides of the house: Printavo orders decode the method from each order's imprint types (screen print / embroidery / heat / personalization; anything else shows as "No method recorded"), and the Chipply production block decodes it from the invoice nickname token. Two things worth remembering: (1) **the real Chipply token vocabulary is EMB / HEAT / PRINT** — a survey of all ~1,240 shell nicknames found EMB (476), HEAT (390), and PRINT (359) dominate, with SCREEN/SP/DTF/ENGRAVED as rare stragglers; the original EMB/SP/DTF assumption came from one sample and would have left ~60% of shells unclassified. The store-detail method badges were expanded to match. (2) **Multi-method orders count in every method bucket** — an order that's both screen printed and embroidered adds its pieces to both chips, so the method pieces can sum to more than the profile's total pieces (317 vs 227 for the test customer). That's intentional — "how much embroidery do we do for them?" — and the section is labeled accordingly. Minor known edge: if a store name itself contained a method word (e.g. "Print Shack EMB:"), the profile query and the badge decoder could disagree on which token wins — not observed in real data.

### Jul 23 — The backup export is a download you can take anywhere (and one subtle bug caught in review)
The Backups page now offers a one-click full export: a ZIP containing every backed-up table as plain newline-delimited JSON plus a manifest describing what's inside — currently ~61 MB, generated in under 20 seconds, readable by any tool without needing this app. Two design notes worth remembering: (1) the export streams straight from the database to the download, so only one export can run at a time — a second attempt while one is running is politely refused; (2) code review caught a subtle trap where **cancelling a download mid-stream would have permanently jammed the "one at a time" lock** until a server restart — fixed and verified by killing a download partway and immediately running a clean second export. Also: the export is a "rolling" copy, not a frozen instant — if the 5-minute sync writes while an export runs, counts can differ by a handful of rows, which is fine for backup purposes.

### Jul 22 — Weekly message rescan narrowed to 60-day-active threads (Tyler's call)
The weekly deep rescan exists to catch replies **we** send (Printavo only signals incoming messages; a thread whose last word is ours never resurfaces on its own). Rescanning all ~8.5k threads took ~14 hours a week and pushed new-message pickup behind the backlog. Now it only rescans threads with a customer message in the last **60 days** (~286 threads today, drains in ~30 minutes). Accepted trade-off: a reply sent on a thread that's been quiet for 60+ days is only captured if the customer later writes back on that thread.

### Jul 22 — Payment requests: deleted users crash the list, the count lies, and no single pass sees everything
Three quirks found while verifying the payment-request backup. (1) **Deleted users poison whole pages:** a payment request whose requesting user was later deleted makes Printavo error out — and unlike the deleted-vendor case on orders, the API returns *nothing* for the entire page (no partial data to salvage). The sync now detects this and re-fetches the page without the "requested by" field, so one deleted user can't kill a backup cycle; a live sweep found several such pages, not just one. (2) **The API's own total overcounts:** Printavo claims 401 payment requests exist, but paging through the entire list end-to-end only ever returns 384 — the other 17 appear to be deleted records still included in the count. The reported total can't be used as a completeness check. (3) **No single crawl sees the whole list:** two complete passes an hour apart each contained ~10 records the other missed (records shift across page boundaries mid-crawl). Because the backup only ever adds records (never deletes) and re-sweeps the full list daily, coverage converges to everything over a few days — our database already held 10 records a fresh live pass couldn't see.

### Jul 22 — What the new-entity backup (B4) covers, and three API limitations found on the way
The backup now also captures **message threads + full message history (with attachment links), inquiries, payment requests, merch stores + their orders, and all account reference data** (users, statuses, delivery methods, payment terms, pricing matrices, email templates, work types, categories, preset task groups) as raw snapshots. Three Printavo API limitations discovered live: (1) **pricing matrix cell values aren't exposed** — the API returns matrix/column structure but no prices or quantities, so matrix contents can't be backed up (nothing we can do); (2) a thread's "regarding" link can only be an Invoice or Quote — merch orders can't appear there, contrary to what the docs imply; (3) a thread's "last message" marker only tracks **incoming** messages, so replies we send don't bump it — a weekly deep re-scan of all threads covers outgoing-only changes with at most ~1 week staleness.

### Jul 22 — What order files can (and can't) be backed up, and the PDF timestamp quirk
File mirroring (backup step B3) copies every order's files into our own cloud storage using links already captured in the database — zero extra Printavo API calls. **Mirrorable without login:** the public order PDF, all artwork mockups, and all uploaded production files (Printavo hosts the latter two on a public CDN). **Not mirrorable:** packing slips (Printavo demands a login — returns 401) and the work-order page (it's a live web page, not a file — and all its data is already in our database anyway). Quirk worth remembering: Printavo **regenerates the order PDF on every request**, stamping the generation time inside the file — so two downloads of the "same" PDF differ by exactly 3 bytes (the timestamp). Any future "verify the backup matches Printavo" check must ignore that field; a plain checksum comparison will always look wrong for PDFs.

### Jul 22 — How the sync is scheduled and what actually syncs each cycle
It does NOT re-read every order every time. **Every 5 minutes:** (1) a line-item status sweep of the newest ~250 invoices (Printavo hides item-status edits from normal change detection); (2) a smart list crawl, newest-first, comparing each order's content fingerprint — always covers at least the newest ~400 invoices / ~150 quotes (telemetry: ~97% of real changes land there), then stops after 3 consecutive unchanged pages; (3) only changed orders are touched further; (4) an "extras drip" pulls the full deep record (mockups, fees, files, approvals) for up to 100 changed/never-captured orders. **Once a day**, one poll runs a full-depth crawl of the whole 12-month window (catches deep edits, worst-case ~24h stale) plus daily payments/details/reference refreshes — that's the single long ~40-min poll. **Never re-synced:** the Feb 2018 → window historical archive is a frozen snapshot; an edit to an ancient order wouldn't be picked up (periodic re-verification is possible later if wanted). The whole design exists because Printavo's rate limit (~10 requests / 5 s, account-wide) forces the budget to be spent where change actually happens.

### Jul 22 — Printavo returns broken data for orders whose vendor was deleted (and we now salvage it)
About 35 older orders can't be fetched cleanly: Printavo's own API errors out with "Cannot return null for non-nullable field PurchaseOrder.vendor" — the order references a purchase-order vendor that was later deleted, which Printavo's schema claims can never happen. The API still sends back everything else about the order alongside the error, so the sync now keeps that partial data (with a note recording exactly what was missing) instead of discarding the whole order. Strict safety rule: partial data is only accepted when *every* error is this exact "deleted-thing" shape — any other error still fails loudly.

### Jul 22 — Those broken orders were silently starving the archive backfill
Because the extras backfill always worked newest-first, the ~35 permanently-failing orders sat at the front of the queue and ate the entire 100-order batch every 5 minutes — the ~16k-order backlog behind them would never have drained. The queue now remembers when each order was last attempted: never-tried orders go first (newest first), and anything that failed cycles to the back instead of blocking the line. Orders that genuinely change still jump straight back to the front.

### Jul 22 — Printavo sometimes times out internally and reports it as a data error
The full-history run died mid-flight on "Timeout on IDed.id" — Printavo's server timing out internally but reporting it like a query problem. Since all our requests are read-only, the client now retries these up to three times with increasing waits (5s/15s/30s) before giving up, so a single hiccup can't kill an hours-long backfill run. The interrupted run was resumed from its checkpoint with nothing lost.

### Jul 22 — Printavo has a hidden 10,000-row pagination window (and the backfill routes around it)
Discovered while starting the full-history backfill: Printavo's order list silently refuses to page past row 10,000. The reported total caps at exactly 10,000 (the real invoice count is ~14–15k), asking for anything beyond row 10,000 returns a generic error, and the list quietly claims "no more pages" right at the boundary. With ~14–15k invoices, no single crawl direction can see them all. **The fix:** the backfill walks the list from both ends — oldest-first for the first 10,000, then newest-first down until it meets where the first pass stopped. The two passes together cover everything as long as the archive stays under 20,000 invoices (currently ~5k of headroom; if the shop ever crosses that, the middle would need a different access path — e.g. searching by order number).

### Jul 22 — Order numbers are NOT in date order
Invoice #1000 was created in 2021, while #4001 dates to Feb 2018. Printavo's visual order numbers were evidently renumbered or reused at some point, so "low number = old order" is unreliable. The backfill sorts by order number (the only stable sort Printavo offers) and simply crawls to the end of the list rather than stopping at a target date.

### Jul 22 — Backup module phase 1: every order now carries a full-fidelity "extras" archive
The sync now captures everything Printavo holds on an order beyond what the Hub displays: fees, expenses, approval requests, production files, custom addresses, thread/payment-request markers, mockup images, personalizations, price receipts, product catalog links, and purchase-order references. It's stored as one raw blob per order (portable for any future migration), refreshed automatically whenever an order changes, and backfilled ~100 orders per 5-minute sync cycle (the ~3,500-order backlog drains in a few hours). The order list itself also fetches every remaining cheap field now — discounts, sales tax, paid-in-full, public PDF link, packing slip link, payment terms.

### Jul 22 — Printavo's 25k complexity cap, measured exactly
The first version of the extras query came back "complexity 29,976 exceeds 25,000" — Printavo computes the cost from the query's page-size limits alone, not the actual data. Lowering the per-page limits (8 groups / 20 line items / 10 imprints / 5 mockups per item) brought it safely under; bigger orders simply take extra paged requests. Useful forever: the error message states the exact computed cost, so limits can be tuned precisely instead of by guesswork.

### Jul 22 — The two "incomplete by design" orders are now stored complete
Orders 20104 and 20714 (more than 20 line-item groups) previously hit Printavo's query cap and were stored partially. The sync now follows a group-by-group cursor past the cap: 20104 went from 26 to 32 stored line items, 20714 from 22 to 94. No orders are excluded from report spot-checks anymore.

### Jul 22 — One-time "rebase wave" after widening the sync
Because every order's fingerprint now includes the newly captured fields, the first sync after this change re-hashes all ~3,500 window orders: one long poll (~35–40 min) and ~3,500 cosmetic "updated" events that don't represent real edits. These get cleaned out of the change log by run ID afterward; real field-level events (status changes, due-date moves) are unaffected.

### Jul 21 — Full backup = full history for every feature (the plan)
The backup module's historical backfill lands in the **same database tables the Hub already reads** — not a separate vault of files (that's how the old standalone backup app worked). Once it runs, a 2019 order looks exactly like last week's order to Reports, order detail, search, and every future feature. Payments already go back to **December 2017** (18,635 transactions); orders currently cover the 12-month window (~3,500) and the backfill adds everything older (~15–19k more). Caveat: history means **records, not timelines** — we get every old order's final state, but not when its statuses changed along the way.

### Jul 21 — Printavo keeps no timestamps or logs for line-item status changes
There is no way to ask Printavo *when* a line item became "Needs Ordering" or "Ordered" — the API exposes only the current status, with no history, no audit log, and no activity feed. It doesn't even bump the order's "last updated" time when a line-item status changes (verified live). **What we did about it:** the Hub now records every product-status transition it observes (old value → new value, timestamped) in its change-events log. Accuracy is within ~5 minutes for recent orders since we can only log when we *notice* the change. The past before this was turned on is unrecoverable. Exception: orders placed through the Hub were always exactly timestamped in the PO Log.

### Jul 21 — How all Printavo traffic shares one throttled pipe
Every Hub feature that talks to Printavo goes through a single gateway that spaces requests 620ms apart (≈8 requests per 5 seconds, safely under Printavo's 10-per-5s account-wide cap) and retries once after a 429. That's why the 5-minute order sync, the task sync (~65 requests worst case), and everything else can coexist without tripping the limit — they queue up behind each other instead of colliding.

### Jul 20–21 — Task-sync flag: one environment only, ever
`PRINTAVO_TASK_SYNC_ENABLED` may be true in AT MOST ONE environment (dev OR published — never both). Each environment keeps its own link table, but both write task "twins" into the SAME live moMINTum database — two enabled environments would each import every Printavo task and create duplicates. Currently ON in dev only, deliberately not shared to the deployment.

### Jul 19 — Mint Bucks test-mode emails still "use up" the real send
Even with emails redirected to Tyler (`[TEST→…]`), a manual poll in the Hub consumes the shared one-shot ledgers (`notification_log`, `reward_awards`) — so the standalone app will never send the real customer email for that order/award. Avoid manual poll triggers on live data until email mode is live or poller ownership has flipped to the Hub.

### Jul 17–18 — Rules for sharing moMINTum's live database
The Hub reads/writes the standalone moMINTum app's LIVE production database. Hard rules that keep both apps safe: member identity resolves **by email only** (oldest row wins); the standalone app's Clerk user IDs are never written from the Hub; missing members are created just-in-time under a database lock (a duplicate-member race was actually found and fixed during testing); Hub-only tables are additive and must never be dropped by the standalone app; every Hub change visible in the standalone app gets a handoff doc in `handoffs/`.

### Jul 16 — Printavo hides line-item status changes from normal syncing
Flipping items to "Needs Ordering" leaves the order's updated-timestamp untouched, so a normal change-detection crawl never notices. That's why the sync engine has a dedicated **product-status sweep**: a slim scan of just line-item IDs + statuses at the start of every sync cycle, diffed against our database, so the Vendor Orders queue stays fresh.

### Jul 13–16 — Vendor pricing semantics (burned us twice)
SanMar's regular cost is **casePrice**, NOT piecePrice — this was gotten wrong twice before it stuck. S&S uses piecePrice. S&S also labels combined sizes like "2/3X". Full notes live in the project memory.

### Jul 13 — Test-order safety rule

### Jul 13 — Printavo's rate limit is account-wide
10 requests per 5 seconds covers ALL apps on the account at once — the Hub shares that budget with Tyler's other live Printavo apps until they're decommissioned. The Hub's 5-minute poll uses ~23% of it, leaving headroom.

### Jul 9–10 — Why the sync re-crawls everything every 5 minutes
Printavo's API has no "give me what changed since X" filter and can't sort by update time (verified against their live schema). The only reliable strategy: re-crawl all orders newest-first every 5 minutes, fingerprint each record (content hash), and store only what actually changed. ~140 requests, ~2.3 minutes per poll.

### Jul 9–10 — Printavo renders timestamps in random timezones
The same instant comes back in varying timezones between fetches. Every fetched record is normalized to UTC before hashing/storing — without this, the sync would log thousands of phantom "changes". This is a permanent rule: never hash a Printavo record without timestamp normalization.

### Jul 23 — Client 360 categories: two bugs worth remembering
1) **Frontend cache keys must match the generated client exactly.** The directory page invalidated queries under the key prefix "/customers", but the generated API client keys everything under "/api/customers…". Nothing errored — the table just silently didn't refresh after assigning a category. Only the end-to-end browser test caught it. Rule: after a mutation, invalidate using the generated key helpers (or a prefix that provably matches them), never a hand-typed guess.
2) **Sorting by spend needs a tiebreaker.** Thousands of customers tie at $0 lifetime spend, and Postgres gives no ordering guarantee among ties — so page 60 could show duplicated/skipped customers between visits. Every paginated ORDER BY now ends with the stable printavo_id.

### Jul 23 — Niche report semantics locked in
Revenue = **invoices only** (order_type='invoice'), same as the existing reports. Including quotes would inflate numbers ~40% (e.g. Abbey Villa $412k vs the real $280k). All-time invoice revenue ~$10.42M across 14.1k invoices; YTD ~$916k. Category deletion is deliberately impossible — categories deactivate instead, so historical report rows always resolve.

### Jul 23 — Directory search now looks inside order nicknames
Searching "soccer" or "paving" finds customers whose ORDERS mention the word, not just their names — e.g. Bishop Guertin High School surfaces under "soccer" via its order history. Combined with the new "Select all N matching" button, categorizing a whole niche is now: search keyword → select all → assign. Note for the future: this scans every order nickname per search (no index); fine at ~19k orders, add a trigram index if it ever feels slow.

### Jul 23 — orval name collision when an endpoint has both path AND query params
Adding query params to getCustomerProfile (which already had a path param) made orval emit a zod schema `GetCustomerProfileParams` (path) and a TS type `GetCustomerProfileParams` (query) — the api-zod barrel's double `export *` then failed typecheck with TS2308. Fix lives in lib/api-zod/src/index.ts: explicitly re-export the zod schema under the bare name and alias the type. Any future endpoint with both param kinds will hit the same thing; same fix applies.

### Jul 23 — customer profile now shows ordering behavior
Order frequency (invoices/month over the customer's active span), average order quantity (pieces per invoice from line items), and top styles (e.g. Abbey Villa = Sport-Tek YST350 youth tees, 21 orders / 1,358 pcs) are computed live per profile view. Frequency is hidden for customers with under ~a month of history so 2 same-week invoices don't read as "8/mo".

### Jul 24 — Ask AI is live: plain-English questions over the order mirror, with saved presets
The new **Ask AI** page (sidebar → Analyze) answers questions like "What was our total invoice revenue in June 2026?" by having AI write a database query against the local Printavo mirror, running it under strict guardrails, and summarizing the result in a sentence — with the table and the exact SQL shown underneath. Two practical limits: answers must finish within ~40 seconds (the hosting proxy kills longer web requests), and results cap at 500 rows — ask for totals/top-N rather than full dumps. ### Jul 24 — Could we get Chipply store data into the hub without an API? (feasibility Q&A)
Tyler asked to revisit options for pulling Chipply online-store data into the hub, since Chipply has no open API. (Note: there is no earlier record of a Chipply discussion in this log or the project notes — the only trace in hub data is Chipply store links inside Printavo production notes — so this entry is the first written record.) Four feasible routes, roughly in order of robustness-per-effort: **(1) Scheduled-email parsing** — if Chipply can send order notifications or, better, scheduled CSV report emails, forward them to a dedicated inbound address the hub watches and parse them automatically; near-real-time and hands-off, but limited to whatever the emails contain and brittle if Chipply changes the format. **(2) Manual export → import page** — download order/roster exports from the Chipply dealer portal and drag-drop them into a hub import page; most reliable and gets historical data, but manual each time. **(3) Portal automation** — a headless browser logs into the Chipply portal on a schedule and downloads the exports itself (same technique the hub already uses to render Printavo pages); fully automatic but brittle to portal redesigns and can be blocked by captchas/2FA. **(4) Ask Chipply** — some platforms quietly offer dealers a data feed, scheduled export email, or partner API even without public docs; one support email could make all of the above unnecessary. Recommended path: ask Chipply about scheduled export emails first; build the import page regardless (its file-parsing machinery is reused by every other route); treat portal automation as a last resort.

### Jul 30 — Feasibility: report of invoice activity by user? (Not by editor — Printavo hides it from the API)
Tyler asked whether we could build a report/view of invoice activity per user (edits, status changes) like the history Printavo shows in its invoice view. Answer: **not by actual editor** — Printavo's API exposes no activity/audit feed, no "changed by" field, and no event timestamps (verified via live schema introspection back when the sync engine was designed). Our own `change_events` feed captures every detected change (created / status change / field change / converted) but only at 5-minute polling granularity and with no attribution. Two honest approximations are buildable today: (1) **activity by order OWNER (rep)** — "invoices owned by X had N status changes / M edits this period" straight from `change_events` + the synced owner field, with the caveat it credits the rep's book, not the person who typed; (2) **true attribution for Hub-driven actions only** — anything done through Hub tools (bulk status changes, purchasing pushes) can be stamped with the logged-in staff member, but direct Printavo edits stay anonymous. Real editor-level reporting would require Printavo adding it to their API, or more daily actions moving into the Hub.
